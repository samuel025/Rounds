# DECISIONS
- 2026-11-06: npm instead of pnpm (not installed). vitest + fast-check for tests.
- 2026-11-06 (M1): Round price solved as P = (V - t*V')/X (derived from X + pool_after = V/P, pool_after = t*V'/P), floored to 4 dp each iteration; SAFE regimes and Cap_pre re-solved per iterate until the price is a fixed point. If top-up would be negative, P = V/(X+B).
- 2026-11-06 (M1): P2 (SAFE holds A/C of pre-round cap) only holds when every SAFE converts at its cap; with a mixed-regime or down round the discount-regime SAFEs enlarge Cap_pre, so the property is checked only on all-cap outcomes. Recorded as a RULES.md clarification.
- 2026-11-06 (spike): near-cli-rs stores demo keys in ~/.near-credentials (legacy keychain), not .state/; they are throwaway testnet keys and never enter the repo. Account names/ids live in .state/suffix.
- 2026-11-06 (M2): GV-2 SAFE 2 shows $305,555.56 although the micro-dollar value floors to .55; vector amounts are rounded half-up to the cent for display only (see RULES.md).
- 2026-11-06 (M2): shortfall dust is reported as remainder, not paid to common (found by P7 monotonicity).
- 2026-11-06 (M3): sandbox tests use a plain account as the "board" instead of the Sputnik wasm. The contract only checks predecessor == board, and the real DAO-as-predecessor path was proven on testnet in the spike. Sputnik-in-sandbox stays a nice-to-have.
- 2026-11-06 (M3): plans travel as canonical-JSON strings; the contract checks sha256(plan bytes) == plan_hash before parsing, so the board approves exactly the bytes the contract will execute. The verifier must produce byte-identical canonical JSON. (Open Q4 answered 2026-11-09 for TS/Python: `ref/conformance.py` now compares canonical bytes and SHA-256 on shared fixtures, including UTF-16 key order and unicode escaping. Rust needs no canonicalizer: it hashes the bytes it receives and parses them with serde_json.)
- 2026-11-06 (M3): the contract credits the plan's issuances as given; it does not recompute equity math (by design: the engine is off-chain, the board approves the hash, anyone re-verifies).
- 2026-11-06 (M3): distribute is capped at 8 payouts per call (25 Tgas each + overhead); answers open Q6 conservatively, not measured.
- 2026-11-06 (M3): the contract does not register payout receivers for NEP-141 storage (open Q5): receivers must already be registered, otherwise their payout fails and stays retryable. The demo script registers everyone first.
- 2026-11-06 (M3): exercise strikes accumulate in the contract (counted in ledger_total) and are not yet forwarded to the treasury; documented gap. (Superseded 2026-11-09: `withdraw_strikes` forwards them, with a retryable callback.)
- 2026-11-06 (M4 web): visual language taken from resend.com's CSS tokens (pure black, hairline borders, Inter + mono, tight tracking, pill buttons, one green accent). Fonts load from Google Fonts with system fallbacks; dark theme only. Vite + vanilla TypeScript, no framework, no charting library (bars are plain CSS).
- 2026-11-06 (M4 web): the page has no wallet. "Propose on chain" prints the plan hash and the exact `near` CLI call instead of sending a transaction; "Run exit" is simulated only. Wallet integration is not built and the page says so.
- 2026-11-06 (M4 web): Verify currently checks the engine against GV-1 and, once deployment.json and events.json are filled by the demo, recomputes each round's plan hash and compares it with the chain. Events and deployment are empty until the testnet deploy.
- 2026-11-06 (M4 demo): in the run above, the vesting check read 37,500 vested (month 18) instead of 25,000: the grant's start time was set before the two DAO votes (~25 s) and the wait began after them, so the demo clock was 6 "months" ahead. The contract and engine agree (37,500 is exactly month 18). scripts/demo.ts now starts the clock 60 s in the future and asserts the exact engine value for month 12 or 13; the committed run predates that fix and has NOT been re-run, so the committed log shows the old check.

- 2026-11-07 (wallet): supersedes the 2026-11-06 'no wallet' decision. The app uses @near-wallet-selector v10 (core, modal-ui, my-near-wallet, meteor-wallet) on testnet, lazy-loaded, with no function-call access key, so every action is approved in the wallet. Meteor needs near-api-js 6 as a peer. The libraries expect Node globals, so the app shims Buffer and process before loading them. A DEV-only `window.__testWallet` hook (compiled out of production builds) lets `scripts/e2e-wallet.mjs` run the app's real buttons with throwaway testnet keys. `npm audit --omit=dev` reports `elliptic` and `decode-uri-component` issues inside the wallet libraries' dependency trees; the app itself never handles keys.

- 2026-11-07 (open sandbox): a Sputnik board cannot be opened to every visitor. A DAO created with an `Everyone` role and threshold 1 is accepted by the factory, but the first `act_proposal` fails with `ERR_UNSUPPORTED_ROLE` (policy.rs: vote counting supports Group and Member roles only). The judge sandbox therefore uses `contract/open-board`: anyone may call `act`, which forwards an allow-listed board method (`set_officer`, `approve_round`, `approve_exit`, `cancel_round`, `add_class`, `terminate`, gas 10..=200 Tgas) to the one Rounds contract it was created for. The Rounds contract is unchanged (it only checks that the caller is its board). The demo run keeps its real 2-of-3 Sputnik DAO. The open board has no unit tests; `scripts/e2e-wallet.mjs` plays the whole judge path against a throwaway sandbox instance.

- 2026-11-07 (self-review of the contract): `close_round` moved the escrow to the board and only then credited shares in `on_close`; if `credit_round` panicked there (unknown class, shares above authorized, a SAFE id that already exists or is already converted) the round stayed Closing with the money gone and no retry. Fixed by `check_creditable`, which mirrors `credit_round` without changing state and runs before the transfer; also `propose_round` now rejects a plan over 64 KiB (an officer, which anyone can be on the open sandbox, could otherwise bloat storage). New sandbox tests: a funded round with 60 issuances closes at the demo's 100 Tgas (the gas concern was checked and not reproduced), and an uncreditable round is refused with the status still Approved, no money moved and the escrow intact. The web app also escapes chain-supplied names everywhere they enter HTML (a plan's holder is any string, and on the open sandbox anyone can propose one); verified with a hostile name in the dev server. Not covered: an independent audit. The already deployed demo and sandboxes run the earlier build.

- 2026-11-09 (P0 hardening, supersedes the "strikes accumulate" decision): exercises still cannot mint shares. `grant` requires the unissued pool to hold the granted shares, and exercising does `move_shares("unissued_pool", grantee, "Common", shares)`, so total common shares are conserved. Exercise strikes are tracked in a separate `strike_balance`; the board calls `withdraw_strikes` to forward them to the treasury, with an `on_strike` callback that re-credits the balance if the transfer fails. `ledger_total` = escrow + exit funds + strikes.
- 2026-11-09 (P0 hardening): `check_creditable` alone still had a close→credit race: two funded rounds naming the same SAFE id could both pass the check and move escrow, then the second callback would panic with the round stuck Closing. `close_round` now reserves the plan's share capacity and SAFE ids (`pending_issued`, `pending_safes`, `pending_converts`) before the FT transfer and releases them on success or failed transfer. A sandbox test runs two closes concurrently with different signers and asserts exactly one wins, one escrow moves, and the loser is not stuck Closing.
- 2026-11-09 (P0 hardening): escrow is forwarded to a `treasury` account passed to `new`, not to the board. The open-board sandbox therefore cannot receive the escrow as a side effect of being the board. `config()` keeps its original return shape so existing readers and `verify-onchain` still work; `treasury()` is a separate view.
- 2026-11-09 (P0 hardening): arithmetic that could wrap is now checked (`checked_add`/`checked_sub`/`checked_mul`/`try_fold`) across deposits, reservations, credits, exits, refunds and the ledger. `new` rejects a zero `month_ns`, a class with zero authorized shares, and duplicate class ids. Engine guards reject a zero solved price, an empty cap table, non-positive pre-money/cap, out-of-range discounts, duplicate SAFE ids, pool targets ≥ 100%, empty waterfall classes, negative proceeds and invalid vesting terms. The Python conformance harness still reports 0 mismatches on 1,000 scenarios (including 40 rejected inputs).

- 2026-11-09 (P0 hardening follow-up): `add_class` no longer overwrites an existing class id or accepts zero authorized shares, so the board cannot silently lower a class's cap under already-issued shares. `propose_round` rejects a non-founder round with any zero raise (which could otherwise close with no money and still credit the plan) and rejects the same investor twice (which would leave a slot that can never be funded). One sandbox test covers all three refusals.

- 2026-11-09 (option-pool claims): `grant` used to check only the pool's current balance, so two grants could each pass and promise the same shares. Grants are now claims on the pool: `grant` needs `pool >= open_claims + new shares`, where `open_claims` sums unexercised shares for active grants and only the vested-at-termination part for terminated grants until the exercise window closes. Exercising reduces the pool and the claim together, so the invariant is preserved; termination and window expiry free claims. Views `open_claims` and `pool_available` expose the totals. A sandbox test covers overcommit refusal, reuse after termination, and expiry after the window.

- 2026-11-10 (follow-up review): strikes being swept stay in `ledger_total` via `strikes_in_flight` until the transfer callback lands, so the ledger never under-reports tokens the contract still holds. Grants are capped at `MAX_GRANTS` (256) because `grant` and the claim views scan every grant. `release_plan` still clamps instead of panicking (a panic in the close callback would strand a Closing round) but emits a `reservation_drift` event if the reservation ever underflows. `cancel_round` already refuses a Closing round; a new sandbox test races a cancel against a close and asserts exactly one wins with no double movement. Not fixed here: the committed testnet demo and sandboxes still run the pre-hardening contract (new `treasury` argument and state layout), so a redeploy and `make demo` re-run is needed before `results/` describes the new build.

- 2026-11-10 (review before submission): four contract changes. (1) The plan hash now covers the money. `propose_round` used to take `kind`, `raise` and `deadline_ns` beside the hashed plan, so an officer could pair an approved share plan with a $1 raise and the board's hash would not show it. A round plan now carries `kind`, `raise` and `deadline_ns` (RULES.md R9, `sealPlan` in the engine) and the contract refuses a proposal whose arguments differ; in a Safe round each investor's raise must equal their SAFE purchase amounts. The call signature is unchanged. (2) `cancel_round` sent one refund per depositor in a loop; with 32 allowed investors that could exceed the gas limit and make a round impossible to cancel. It now refunds at most eight, and only as many as the attached gas covers, and the rest are pulled with `retry_refund`. (3) Money paid into an exit could not come back if the board never approved it. Exits now record their funders (at most 16); the board can `cancel_exit` until the first payout is sent, and funders pull exact refunds with `refund_exit` (retryable callback). (4) `close_round` needs 100 Tgas, the gas the 60-issuance test closes with (was 60). Three new sandbox tests; the demo adds a fourth on-chain attack (an officer proposing the approved Series A plan with a $1 raise). Not changed: a second payout plan over the same holdings is still possible and is documented as the board's decision.
- 2026-11-10 (shared payout, R10): added a shared-treasury payout so the project shows what a group does with a DAO, not only a cap table. No contract change: the plan is an exit plan (`payouts`), so approve-by-hash, pay-once and retry already apply, and the DAO funds it from its own treasury (a FunctionCall proposal on the token; the funder is recorded, so `cancel_exit`/`refund_exit` would return it). Pro rata by shares across all classes, floor division, remainder reported and left in the treasury, unissued pool excluded (RULES.md R10, `proRataDistribution` in the engine). It runs as a separate script, `make distribute`, against the committed demo deployment, because a full `make demo` needs about 26 testnet NEAR and the faucet was refusing; the script appends its transactions and events to the committed run. A fresh `make demo` does not include step 10 until `make distribute` is run on it. Not in the Python reference.
- 2026-11-10 (voter review, SAFT model): (1) `web/src/review-core.ts` decodes a Sputnik proposal and re-checks the hash it carries against the plan the contract holds; `web/src/review.ts` draws it in a Board proposals card, adds a vote button that is disabled on a mismatch, and lets a board member put a round to the board with a description written from the plan. No contract change. The check is only as good as what the contract stores: exit plans are rebuilt from the stored payouts (the plan is `{payouts}`), so a proposer's file is not re-hashed. (2) The engine gained a SAFT / token-warrant conversion model (R11, `src/engine/saft.ts`) with hand-derived vectors and a property test. It is engine-only: no contract, app or demo support, and not in the Python reference, because a token reserve and token grants are about two days of contract work plus a testnet redeploy that the faucet and the remaining testnet NEAR do not allow before the deadline. README says so under "Next: tokens and SAFTs".
